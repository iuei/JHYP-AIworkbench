# M-D 准备：产品主数据打通库存与销售（交付记录）

> **状态：已交付（2026-09-11）**。验收：单测 271/271、`verify-e2e --live` 21/21、`verify-ui` 38/38。
> 注意：本轮与另一条并行轨道（M-C 知识沉淀）同时开发，本文档只描述本轨道改动。

**Goal:** 让"可售天数 / 断货 / 滞销"这些库存判断建立在**真实销售历史**上，而不是订单快照的几天样本。

## 问题（M-B 遗留的明确局限）

库存快照按 SKU 记录，销售报告按 ASIN 记录，两者**无法关联**。因此 M-B 只能用订单快照估算日均销量，而订单快照只是近期切片。
实测后果：`KT-JH-001-BK` 用 3 天样本算日均 3 件 → 可售 133 天 → **判定"积压"**。这个结论会让运营去清库存，而实际该 SKU 日均卖 9.27 件、可售 43 天，完全健康。

## 交付内容

| 项 | 说明 |
| --- | --- |
| `product_master` 数据集 | SKU ↔ ASIN/站点映射（含商品名称、分类、状态，**不含采购成本等敏感字段**） |
| 迁移 109 | `CREATE TABLE product_master`（`UNIQUE (sku, marketplace)`，ASIN 与 SKU 双向索引） |
| 迁移 110 | 工具契约重播（`analyze_inventory_risk` 新增 `velocityWindowDays` 参数） |
| `computeSalesVelocityFromSales` | 按 SKU→ASIN 映射，用销售报告在指定窗口内算日均销量 |
| `resolveVelocityWindow` | 统计窗口以**数据自身最后一天**为锚点（不是"今天"——报表是滞后数据，用今天会得到空窗口） |
| `mergeVelocitySources` | 两种口径合并：销售报告优先，缺失回退订单快照并标注来源与置信度 |
| `analyze_inventory_risk` 增强 | 新增 `velocityWindowDays`（7–180，默认 30）；输出带「销量口径」列 |

## 效果（同一份模拟数据，前后对比）

| SKU | 改造前（订单快照 3 天样本） | 改造后（产品主数据 → 销售报告 30 天） |
| --- | --- | --- |
| KT-JH-001-BK | 日均 3 → 可售 133 天 → **积压** ❌误报 | 日均 9.27 → 可售 43.1 天 → **健康** ✅ |
| KT-JH-002-BK | 日均 3 → 建议补货 123 | 日均 4 → 可售 3 天 → 建议补货 **168** |
| 未登记的 2 个 SKU | — | 明确提示「未在产品主数据中登记，无法关联销售数据，建议先补齐」 |

模型在回答里如实转述了口径与窗口：
> **销量口径**：KT-JH-002-BK 与 KT-JH-001-BK 使用「产品主数据 → 销售报告」的完整销售历史计算，统计窗口 2026-08-01 ~ 2026-08-30（30 天），可售天数判定可采信。
> **需要注意的两点**：HM-JH-011-S、OD-JH-007-WH 这 2 个 SKU 未在「产品主数据」中登记，无法关联销售数据，因此无法评估其断货/滞销风险。建议先补齐产品主数据（SKU ↔ ASIN 映射）后再做评估。

## 关键设计决策

1. **窗口锚点用数据最后一天，不用今天**：报表人工导出、天然滞后。用今天做锚点会得到一个没有数据的空窗口，进而把所有 SKU 判成"无销量"。
2. **区分"没卖出去"与"报表没覆盖"**：映射到的 ASIN 在窗口内**完全无记录**时标记 `hasCoverage = false`，回退其他口径；只有在报表确实覆盖了这些日期、销量为 0 时才判滞销。否则会把"没导入数据"误判成"卖不动"。
3. **口径必须在回答里说明**：销售报告口径可采信，订单快照口径样本短、置信度低。两者混用而不说明，等于让用户拿不同可靠度的结论做决策。
4. **主数据是快照语义**：覆盖导入 = 整表替换（沿用 M-B 对无周期列数据集的覆盖语义）。
