## 任务目标

`/settings`（用户信息页，入口为顶部头像与侧边栏底部用户区域）原先放了两个**可编辑的演示表单**：

| 表单 | 字段 | 实际行为 |
| --- | --- | --- |
| 个人资料 | 姓名 / 邮箱 / 部门 | 只调用 `showSubmittedData`（弹 JSON toast），无接口、不落库 |
| 账户信息 | 工号 / 角色 | 同上 |

问题有三层：

1. **假功能**：改完刷新即丢，用户却以为改成功了。
2. **权限误导**：`角色`是权限依据（`server/index.mjs` 用 `user.role` 决定 `isAdmin`），`工号`就是 `login`（账号主键），让用户自填等于让用户以为能改自己的权限与身份。
3. **职责重叠**：姓名和角色的配置权本来就在管理员侧「设置 → 用户管理」（`PATCH /api/users/:id`），用户侧那份是重复且不生效的。

**目标**：把配置权收归管理员，用户侧改为只读展示 + 退出登录。

## 用户确认的方案

- **方案 B**：只读个人信息 + 退出登录，**不**新增自助改密码接口（不动服务端登录链路）。用户忘记密码仍由管理员重置。
- **部门字段**：保留，并纳入管理员配置 —— 这意味着需要落库，因此本次**包含服务端与数据库结构改动**。

## 踩过的坑

| 现象 | 根因 | 规避方式 |
| --- | --- | --- |
| `pnpm run test` 直接失败：`Executable doesn't exist ... chrome-headless-shell` | 本机没有 Playwright 自带 Chromium；`pnpm exec playwright install chromium` 在本环境下载卡死（5 分钟无输出） | 用**系统 Chrome**：临时 vitest 配置里把 provider 换成 `playwright({ launchOptions: { channel: 'chrome' } })`，再 `pnpm exec vitest run --config <临时配置> --browser.headless`。配置文件要放在工作区根目录（否则插件与 `@` 别名解析不到），验证完删除 |
| `getByText('管理员')` 报 strict mode violation，命中 4 个元素 | vitest 浏览器模式的 locator 走 Playwright 语义，`exact` **默认 false**（子串匹配），段落里的“管理员”也会命中 | 断言短文案时显式写 `{ exact: true }`；或改用 `getByRole('heading'/'button', { name })` |
| 新增迁移如果图省事复用 version 1 或 100 起的号段 | 迁移器以 `schema_migrations.version` 为唯一键，撞号会被当成「已应用」**静默跳过**（表结构不变但迁移不报错） | 用户表迁移取 version 2（1 属快捷导航、100+ 属 AI 助手）；新增 `user-migrations.node-test.mjs` 断言 `version > 1 && < 100` 守住约束 |
| 老调用方 `PATCH /api/users/:id` 只传 `name` + `role`，可能把用户已有的部门清空 | 直接把缺失字段当空串处理 | `parseUserUpdate` 对缺失 `department` 返回 `null`，SQL 用 `COALESCE($3, department)` 保留原值；显式传空串才是清空。**新增可空字段时优先想「未传」与「传空」是否同义** |
| 删除两个假表单后担心别处还在 import | 用 grep 先确认引用面 | 实际只有 `profile/index.tsx` 引用；`/settings/account` 的旧路由重定向与它们无关，保留 |
