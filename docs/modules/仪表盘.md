# 责任田：仪表盘

## 功能描述

负责登录后首页（`/`）的个人工作台：快速进入真实业务、查看自己的 AI 使用状态与最近活动。

首页只承担工作台职责：**不展示 AI 治理内容**（团队知识管理、数据源、经验审核、模型配置、审计台；员工的个人知识库入口仍保留），**不展示没有路由或没有数据支撑的伪功能**（历史版本出现过「即将上线」的占位卡片）。治理入口保持在管理员侧的「AI 治理」导航分组。

## 功能清单

- **工作概览（2026-09-20 置顶）**：全宽卡片内等宽展示四项数字 —— 需立即处理 / 分析记录（都标注「最近 20 次内」的扫描范围）/ 最近对话 / 知识沉淀（有待审时补「待审 N 条」）。数据来自已有分析与 AI 查询，不新增经营指标；分析与 AI 的加载、错误状态分别处理，失败不显示误导性的 0。窄屏两列，扫描范围提示另起一行，数值保持对齐。
- 主操作区「开始工作」：三个**带上下文**的动作 —— 「继续上次分析」（没有历史记录时不渲染，点开直接是最近一条快照）、「新建分析」（`/competitor-analysis?focus=asin`）、「问 AI」（`/ai-agent?focus=composer`）。操作区与常用入口合为一张卡；宽屏与「需处理的分析」同排等高，窄屏先显示操作区。
- 常用入口：**三项**有真实路由的入口，支持拖拽排序与键盘排序，顺序持久化。
- 常用入口展示：位于「开始工作」卡片内，一行一项（图标 / 名称 / 说明 / 行内排序按钮），保留拖拽、键盘排序与持久化；接口读取失败时按默认顺序展示并提供局部重试。
- 需处理的分析（2026-09-15 新增，**2026-09-17 改数据表格**，**同日起改为"未销账"口径**）：`GET /api/competitor-analyses?limit=20` 的结果里 **`openLevel='high'`** 的记录（服务端算出的"扣掉已销账 / 已核验 / 已忽略之后，仍未处理问题里的最高级别"），最多 3 条，点「回看」打开那条快照。桌面表格列为 结论 / ASIN / **待处理** / 时间 / 操作（"待处理"= `openFindingCount`，不是快照结论总数）；窄屏改为紧凑记录行，直接显示「回看」按钮，不再要求横向滑动。**用户在结论卡片上点「标记已处理」或「不处理」后，这条记录就不再计入（连同概览统计的「需立即处理 N」一起降下去）**。**两种空态必须区分**：扫描范围内没有 high（"最近 20 次分析里没有需要立即处理的问题"）与一条记录都没有（"还没有分析记录，做完一次分析后这里会列出需立即处理的问题"）。卡片描述写明扫描范围，底部给出消除提醒的操作路径。
- 工作动态：桌面端与首排一致的 8:4 分栏，两个卡片同排等高 —— 左侧「最近分析」（最近 5 条，表格：查询 / 站点 / 问题数 / 严重度 / 时间 / 操作），右侧「我的 AI」（最近 3 条对话，点击**直接进入该会话**；沉淀总数与待审核数）。窄屏纵向排列，「最近分析」改为紧凑记录行并保持操作按钮可见。
  - **「严重度」列与竞品分析的「历史分析」表同口径（2026-09-17 第二次修正）**：渲染 `openLevel`
    （**扣掉已销账 / 已核验 / 已忽略**之后仍未处理问题的最高级别），有销账时补一句「已销账 N 条」。
    两处**共用同一个组件** `@/features/competitor-analysis/components/history-level-badge`，
    不要各自再写一遍 Badge —— 上一版这里用快照 `level`，用户销账后首页仍显示「需立即处理」，
    与「需处理的分析」自相矛盾（用户实测报的就是这一类问题）。
    「问题数」列同样属于快照口径（`findingCount`），**只有「需处理的分析」那张卡用未销账计数**。
  - 「最近分析」**刻意不显示结论摘要**：这一块回答"做过哪些分析、结果严不严重"，结论详情在快照里读；把 `headline` 也摆上来会让每行变两行、把列表重新拉高。`index.test.tsx` 有断言守住这一点。
  - 为什么换掉原来的「正在进行的工作」：它读的 `work_items` 表只由竞品分析写入**一条 progress 固定 65 的假任务**，全仓库没有任何更新入口（实测库里 0 行）—— 界面长期是空态，一旦产生又永远挂着、也清不掉；与此同时首页完全不体现项目的真实使用重心（AI 问答与知识沉淀）。该表已停止写入，首页也不再读取它。
- 状态处理：查询中用 `Skeleton`；查询失败给出「重新加载」按钮并可重试；空数据展示明确空态且不隐藏区域；排序保存失败保留本地顺序并 toast 提示。
- 可访问性：拖拽不是唯一排序方式（每张卡片有带 `aria-label` 的上移/下移按钮，首尾自动禁用）；顺序变化用 `aria-live` 播报；装饰性图标一律 `aria-hidden`。
- **无页面标题横幅**：页面名「仪表盘」由全局 `Header` 从路由 `staticData.title` 渲染。改造前这里有一个 `text-2xl` 的 h1「JHYP 智能工作台」加一句口号，占掉首屏两行，且它只是应用名/口号、不是内容重点。

## 旧偏好兼容策略

数据库里可能仍存着历史用户的旧 `shortcut_ids`。归一化由前端 `normalizeShortcutIds`（`src/features/dashboard/shortcuts.ts`）负责，规则为：

1. 丢弃无法识别的 ID；
2. 丢弃重复 ID，保留首次出现的位置；
3. 保留仍然有效的 ID 的原有相对顺序；
4. 缺失的入口按默认顺序追加到末尾；
5. 因此无论输入多脏（空数组、非数组、只剩旧 ID），结果恒为当前全部有效入口。

不做数据迁移、不删除既有用户偏好：旧记录经归一化后即可正常渲染，用户下次调整顺序时会写回新 ID。

## 入口与出口

- 入口：`src/routes/_authenticated/index.tsx`。
- 出口：`/ai-agent`、`/knowledge`、`/competitor-analysis`。

## API 明细

- `GET /api/dashboard`：返回 `workItems`、`shortcutIds`（入口顺序，可能是历史 ID）、`analyses`（最近 5 条竞品分析）。其中 `workItems` 与 `analyses` **首页都已不再读取**（`analyses` 那套字段没有时间、没有结论分级、没有问题数），服务端保留这两个字段只为不破坏既有响应契约。
- `GET /api/competitor-analyses?limit=20`：首页一次拉取（query key `['dashboard','recent-analyses']`），**同时供「概览统计」「需处理的分析」「最近分析」三块使用**；返回富字段摘要 `headline`/`level`/`findingCount`/`createdAt`/`marketplace`/`asins`，以及 **`openLevel` / `openFindingCount`（未销账口径）**。`level`/`findingCount` 是**那一次分析的快照判定**（「最近分析」的「问题数」用快照条数）；`openLevel`/`openFindingCount` 是**当下还要处理什么**（需处理的分析与概览统计用它，「最近分析」的严重度也用 `openLevel`，与竞品分析历史表保持一致）。老记录缺 `openLevel` 时前端回落到 `level`。**query key 不得复用竞品分析页的 `['competitor-analyses']`**：那边 `limit` 是 10，React Query 同 key 共享缓存会让两个页面互相覆盖条数。
- 深链出口：`/competitor-analysis?analysisId=<id>`（分析记录快照）、`/competitor-analysis?focus=asin`、`/ai-agent?focus=composer`、`/ai-agent?conversationId=<id>`（会话）。四个参数都可选，脏值由各模块的 `search-params.ts` 忽略。
- `PUT /api/dashboard/shortcuts`：保存当前用户入口顺序。
- `GET /api/ai/conversations`：「我的 AI」的最近对话（取前 3 条）+ 概览统计的「最近对话」总数（同一份响应）。员工可读接口，不需要管理员权限。
- `GET /api/ai/notes?page=1&pageSize=1`（可带 `status=pending`）：首页只取响应里的 `total`，用于概览统计的「知识沉淀」以及卡片里的「共 N 条 / M 条待审核」。用 `pageSize=1` 是为了让服务端少读数据。
- **概览统计不新增任何接口**：四个数字分别来自上面两份数据（分析记录条数与未销账 `openLevel='high'` 条数、对话条数、沉淀 total 与 pending total；老记录按 `level` 回落）。
- 服务端在没有偏好记录时返回 `server/dashboard-shortcuts.mjs` 的默认顺序。

## 依赖关系

- 依赖：`src/components/layout/`、`src/components/ui/`、`DataTable` + `src/lib/table-styles.ts` 的列语义常量、`src/features/dashboard/shortcuts.ts`、React Query 与 `src/api/client`；**跨模块复用**：`src/features/competitor-analysis/api.ts` 的 `fetchAnalysisHistory`（取历史摘要）与 `format.ts` 的 `FINDING_LEVEL_LABELS` / `FINDING_LEVEL_VARIANTS`（严重度文案与徽章样式，不另写一套映射）。同类跨模块复用已有先例：`my-ai-card.tsx` 复用 `@/features/ai-agent/format`。
- **模块内分层**：`index.tsx` 编排版式与排序（`ShortcutSection` / `ShortcutCard`）；`overview-stats.tsx` 渲染工作概览，`use-my-ai.ts` 提供「我的 AI」查询，`analyses-cards.tsx` 渲染两个表格块，纯逻辑在 `analyses.ts` / `shortcuts.ts`。
- 被依赖：全局首页路由和后台默认入口。
- 共享字段：`shortcutIds` 的默认顺序同时存在于服务端（`server/dashboard-shortcuts.mjs`）与前端（`src/features/dashboard/shortcuts.ts`）。改一处必须同步改另一处，否则新用户的首屏顺序会与前端定义的默认顺序不一致。两处都有单测守住「只含三个真实入口、不含已下线占位 ID」。

## 影响范围

修改仪表盘可能影响首页首屏信息结构、主题适配和移动端布局。首页是登录后默认落地页，改动会影响所有角色的第一印象。

**2026-09-20 重构影响**：首屏由「概览和入口分散排列」改为「需处理分析 + 开始工作」双主区；工作概览位于待处理卡片下方，窄屏依次显示开始工作、待处理、概览、最近分析与我的 AI。常用入口成为开始工作卡片的扁平列表。真实页面取景发现待处理表格的「回看」按钮被横向挤出视口，现固定列宽使宽屏操作直接可见；复核时 `main` 高度从 1105px 收敛到 967px。快捷入口顺序接口故障只影响入口排序，其它分析与 AI 数据区继续显示。统计的需处理条数按最近 20 次内全部未销账 high 记录计算，表格仍只展示最近 3 条。仅影响仪表盘 UI、测试与文档；路由、API 契约、权限和数据库不变。

**2026-09-20 再优化影响**：用户反馈两列卡片参差不齐，并明确要求工作概览最上方。现将工作概览改为全宽置顶卡片；下面两排统一 8:4 列宽、各排卡片等高，卡片标题与内边距统一。常用入口收紧为单行，桌面首排高度约 281px；AI 无对话时空态垂直居中。390px 窄屏的分析区改用紧凑记录行，「回看」直接可见；真实页面检测 390px 和 1024px 均无页面级横向溢出。只改仪表盘展示和测试，不变更 API、权限或数据。

**2026-09-17 版式重构的实测影响**（1680×1000，真实数据）：整页 `main` 高度 **1195px → 975px**，首屏从"只能看到告警"变成"概览 + 主操作 + 常用入口 + 全部 3 条告警 + 最近分析头部"。分块变化：常用入口 **199px → 82px**、需处理的分析 **880px → 319px**。**接口、服务端、载荷、数据库零改动**；`index.test.tsx` 的 17 项守护断言**一条未改**（排序按钮契约、两种空态文案、响应式列数、无 `headline` 展示、无治理词汇、`h1` 数量为 0 全部保持）。

列表渲染需注意：工作动态区域的 grid item 必须带 `min-w-0`。grid item 默认 `min-width: auto`、列宽又是 `1fr`（最小值为 auto），一旦列表里出现 `truncate` 的长标题就会把整列撑宽、把页面顶出横向滚动（已由 `index.test.tsx` 的横向溢出断言守住）。

## 修改边界

- 可以改：仪表盘内部卡片、分区组件、空态、加载态、错误态和入口定义。
- 绝对不能动：无需求不得修改全局布局、认证路由分组、主题变量命名和其他模块页面结构。
- 不得把 AI 治理内容（团队知识管理、数据源、经验审核、模型配置、审计台）放进首页，也不得在首页新增经营指标类伪数据；个人知识库仍是员工入口。

## 注意事项

- **概览统计与「我的 AI」共用一份查询（2026-09-17）**：三个 AI 侧查询抽到了 `use-my-ai.ts` 的 `useMyAiSummary`，统计行与卡片都调它。**不要在 `index.tsx` 里再写一遍 `useQuery`** —— React Query 虽然会共享缓存，但两处各写一份等于把 query key 与 `pageSize=1` 这类口径复制了一份，改一处漏一处就会出现"统计说 3 条、卡片说 5 条"。
- **截断列要 `min-w` + `max-w`，不要 `max-w-0`（2026-09-17，踩过，实测）**：两个表格的"结论 / 查询"列最初写成 `max-w-0 truncate`（宽屏好看），结果窄屏（390px）下整列被压成 `B…`、内容完全读不出来。改为 `min-w-[16rem] max-w-[32rem] truncate` 后，窄屏由**表格自己横向滚动**承担溢出，页面级仍然无横向滚动（`dashboard-redesign-check.mjs` 有断言）。
- **统计项的文案不要和别处逐字重复（2026-09-17，踩过）**：统计行最初给"知识沉淀"配了「N 条待审核」，与「我的 AI」卡片里的徽标同字 —— 同一句话在首屏出现两遍既啰嗦，又让 `page.getByText('2 条待审核')` 同时命中两个元素、测试 strict mode 直接失败。现在统计行写「待审 N 条」（标签式），徽标保留「N 条待审核」（句子式）。
- **统计口径必须写在标签里**：「分析记录」与「需立即处理」都只覆盖最近 20 次扫描范围，不写清楚会被读成全库统计（与「需处理」卡片描述同一条口径）。
- 当前是内部工作台首页，不展示模板销售、收入、订阅等伪数据。
- 入口卡片只放有真实路由、有真实数据的入口；新增入口前先确认路由存在。
- 排序保存失败时**不能**让顺序回退：`pendingOrder` 保留用户的本地顺序，只提示失败。
- 保存成功后不清空 `pendingOrder`，否则界面会在重新拉取完成前闪回旧顺序。
- 拖拽只从卡片主体（`Link`）发起，避免按住排序按钮时误触发拖动。
- 组件按分区拆分：`index.tsx` 内保留 `ShortcutSection` / `ShortcutCard`，纯逻辑与入口契约在 `shortcuts.ts`、分析数据的筛选与时间格式在 `analyses.ts`、类型在 `types.ts`、卡片在 `my-ai-card.tsx`（复用 `useMyAiSummary`）与 `analyses-cards.tsx`（需处理 + 最近分析，同源一次查询）。
- 首页的时间显示按**本地时区**计算（`analyses.ts` 的 `formatRelativeTime`），不得改成 `toISOString().slice(0, 10)` 这类 UTC 切片：东八区凌晨会整体早一天（AI 助手模块的 `formatDate` 就是这个写法，属该模块的独立改动）。
- 排序保存的失效范围必须是 `{ queryKey: ['dashboard'], exact: true }`：去掉 `exact` 会前缀命中本页的分析查询与「我的 AI」的三个查询，每次拖动入口都多发四个请求。
- 分析卡片的骨架高度要与真实行高对齐（需处理 `h-20`、最近分析 3 × `h-16`）：骨架比内容矮会让首屏在数据到达时跳动。
- 测试里的 `Link` mock 必须支持 `search`：首页的深链全部在 `search` 里，只拼 `to` 会让 analysisId / conversationId / focus 的断言全部失效（`index.test.tsx` 的 mock 已按此实现）。
- 「需处理」与「最近分析」**同源一次查询**，因此共用同一份 loading / error 状态，失败时两处一起降级 —— 这是设计内的联动，不是两个独立缺陷。
- 「我的 AI」只允许员工可用的「个人知识库」，不得出现 AI 治理、数据源、经验审核、模型与配置、审计台等治理入口：`index.test.tsx` 有守护断言。
