# 责任田：竞品分析

对**一组 ASIN**（第一个为「本品」，其余为对比对象）做真实广告与销售表现的横向对比，并给出确定性结论。
**2026-09-16 起**：竞品的公开数据（价格/评分/BSR/月销量趋势/流量词/评论/类目市场）由**卖家精灵 MCP** 提供，
因此本页第一次能真正对比**第三方竞品**，而不再只是「同一份自家报表内的 ASIN 横向对比」。

## 两套数据、两种口径（最重要的前提）

| 来源 | 覆盖对象 | 得到什么 | 性质 |
| --- | --- | --- | --- |
| 自家报表（广告日报 / 业务报告 / 库存快照 / 产品主数据） | **本公司**的 ASIN | 广告花费、销售额、订单、ACoS、转化率、库存与可售天数 | 真实经营数据 |
| 卖家精灵 MCP（公开数据） | **任意** ASIN（含第三方竞品） | 价格、评分、评分数、BSR、上架时间、卖家数、月销量趋势、流量词、差评、类目市场结构 | 第三方**估算**数据 |

**两者绝对不能混算**（不能把卖家精灵的月销量与自家报表销量相加或相除，不能用一方做另一方的分母）。
页面上由 `Finding.scope`（`local` / `public`）分成两个结论分组、并在每个公开数据块上挂 `note` 说明来源。

## 边界与接口

- 页面路由（**一个模块三个路由**，2026-09-16 起；当天稍后按用户口径重排）：
  - `/_authenticated/competitor-analysis`：**分析页** —— 只放「要分析什么 + 分析过什么」：
    参数设置（完整表单）+ 历史分析表，**不承载任何结果**
  - `/_authenticated/competitor-analysis/results`：**分析结果页** —— 一次分析的全部产出：
    顶部**一张合并卡**（结论与建议 + 判定 + 这次分析是谁 + 区间 / 环比 + 一句话结论 + 分组结论列表 +
    底部一行数据来源）+ 全部数据块（含商品卡片）；原名「数据明细」，2026-09-16 按用户口径改名并把结论一并并入；
    **"结果头卡 + 结论与建议卡"已于 2026-09-17 合并成一张，底部的「数据口径与未接入维度」卡同期删除**

    不是别人要找的目标；顶栏里它算作「分析」（高亮口径见组件注释）

## 商品数据的两种读法：卡片（默认）与表格（2026-09-16）

用户口径：「竞品分析的数据应该使用卡片展示，包含图片，用户点击卡片后跳转到单独页面，页面内是该竞品的详细内容」。

- **卡片视图（默认）**：一个 ASIN 一张卡，带卖家精灵主图（`publicData.rows[].imageUrl`，服务端一直在回传，
  此前没有任何地方展示），点整张卡进 `/competitor-analysis/$asin`；卡片集合以**本次分析的 ASIN 全集**为准
  （`buildProductViewItems`）——卖家精灵漏收录的 ASIN 也要出现（显示"未收录"，点进去仍能看到自家报表那一侧），
  不能因为没收录就从列表里消失。
- **表格视图（可切换）**：仍是服务端生成的同一块（`buildPublicProductBlock`），只是换一种读法。
  切到表格的能力必须保留：横比多个 ASIN 的价格 / 评分 / BSR 时表格更直接，而且这一页刚按
  「内容优先用数据表格」的口径表格化过，删掉表格是开倒车。偏好存 `localStorage`（`competitor-product-layout`，读失败回落卡片）。
- **块的摘取靠结构化标记，不靠标题文字**（`src/features/competitor-analysis/product-view.ts`）：
  服务端给该块打了 `dataset: 'sellersprite_products'`，快照里没有这个字段的老记录靠"列键与
  `PUBLIC_COLUMNS` 逐项一致"兜底 —— 标题是给人看的文案，改一个字就会让识别静默失效（表现为"表格不见了"）。

### 详情页为什么只读快照（改这块前必读）

卖家精灵**按调用次数计费**，点开一张卡片就再花两次调用不可接受；而且详情页要说的是"这次分析看到了什么"，
重新取数会让同一批 ASIN 在主页面与详情页出现两套数字。因此详情页**只读已落库的快照**，
抽取逻辑是纯函数 `selectAsinDetail`（`asin-detail.ts`，有单测），按结构化字段筛选：

| 内容 | 筛选判据 |
| --- | --- |
| 商品公开属性 | `publicData.rows[].asin` |
| 自家报表表现 | `comparison.rows[].asin` |
| 库存与可售天数 | **只对本品**（竞品不在产品主数据里，服务端也只算本品） |
| 月销量趋势 | 图表块的 `series[].key`（就是 ASIN） |
| 流量结构 / 评论概况 | 指标项的 `key` 后缀（`total-<ASIN>` / `avgStar-<ASIN>`） |
| TOP 流量词 / 差评高频词 | 表格行里的 `asin` 字段 |
| 相关结论 | `evidence` / `detail` 里**词边界**命中该 ASIN（`B0ABCDEFGH` 不能被 `B0ABCDEFGHI` 误命中） |

**组级信息（自家报表的期间汇总、环比、组内对比图、「本品 vs 竞品均值」）不进详情页** ——
它们不是任何一个 ASIN 的属性，放进单 ASIN 页面会被读成"这个 ASIN 的数字"。库存与店铺可用性同理只给本品。

## 页面分工：结论留主页，明细进子页（2026-09-16）

**动因（用户口径）**：「当前竞品分析页面展示内容过于复杂，不方便用户查看阅读，且主次不明确」。
**实测依据**（记录 #32，1080 视口）：主页总高 **4499px ≈ 4.2 屏**，其中输入表单 466px、
自家横向对比表 504px、商品卡片 724px、公开口径与趋势/流量词/评论 600px+、口径说明 374px、历史 448px，
而**最该先看的「结论与建议」只有 666px（15%）**，还被夹在表单与明细之间 —— 首屏只装得下
"表单 + 结果头卡"。经选项确认走「结论留主页 + 新增数据明细子页」+「有结果时表单收起」。

| 页面 | 放什么 | 不放什么 |
| --- | --- | --- |
| 分析页 `/competitor-analysis` | **只有两件事**：参数设置（完整表单）+ 历史分析表 | 结论、数据块、商品卡片、口径声明（**全部**在结果页） |
| 分析结果页 `/competitor-analysis/results` | **一次分析的全部产出**：顶部**一张合并卡**（结论与建议 + 判定 + 这次分析是谁 + 区间 / 环比 + 一句话结论 + 分组结论列表 + 底部一行数据来源，2026-09-17 由"结果头卡 + 结论卡"合并）、全部数据块（本品自家报表 → 横向对比 → 按日对比 → 库存联动 → 商品卡片与公开数据） | 参数设置（改参数回分析页）、**底部的「数据口径与未接入维度」卡（2026-09-17 按用户口径删除，见「顶部结论区的排版口径」第 6 条）** |
| 竞品详情页 `/competitor-analysis/$asin` | 单个 ASIN 的属性/趋势/流量词/评论/自家表现/相关结论 | 组级块（见「详情页为什么只读快照」） |

**分析成功后自动进入结果页**（用 push 而非 replace：用户在结果页点「返回竞品分析」能回到分析页再跑下一次）。
分析页因此**不再有"有结果时收起表单"的状态** —— 组件在跳转时卸载、`result` 不保留，
原先那套「参数摘要条 + 本次分析已完成卡」永远不会显示（死代码），已随本轮删除。

**返回链接不带 `analysisId`**：分析页收到该参数会立刻转发回结果页（那是给首页深链用的），
带上它点返回就会来回弹（**实测踩到的死循环**）。`analysisId` 仍用于右侧"当前查看…分析记录 #N"的显示。

关键规则：

- **输入表单有结果后收起**（`[data-form-expand]` 展开）：`showForm = result === null || formOpen || autoFocusAsin`。
  无结果、用户点「修改参数，重新分析」、或首页 `?focus=asin` 深链进来时仍展开。
  收起时渲染的是**一行参数摘要**（ASIN 列表 + 站点/区间/对比基线 + 已取维度），
  读结论时仍知道"这是哪个区间、哪几个 ASIN"。
- **结论的主次靠排序与折叠表达**：`FindingsPanel` 组内按严重度排序（稳定排序，不改数据），
  `info`（提示级）默认收起、显式展开 —— 它与"需立即处理"不该抢同一屏。
- **明细页不重复渲染结论**，主页不重复渲染数据块：一条信息只有一个归属页面。
- 明细页的数据块**沿用服务端顺序**，不按标题文案重新分组：标题是给人看的文案，
  按它分类一旦被改动就会静默错位。

**子页不带 `analysisId` 直接打开时自动回落**（用户口径：「为什么没有直接展示在子页面」）：
子页现在是导航里的独立入口，点进来时 URL 上没有记录 id —— 此时**不给"缺少 id"的空态**，而是
明细页取**最近一次有快照的分析**、竞品详情页取**最近一次包含该 ASIN 的分析**（拉 20 条摘要里筛，
因为最近一次分析未必包含这个 ASIN），页面顶部说明"未指定分析记录，自动打开最近一次（#N）"。
真的一条都没有时才给空态并引导去分析页。
查询键刻意不复用主页的 `['competitor-analyses']`（那边 `limit=10`，同键会互相覆盖条数）。

**明细页的摘要卡只留三件事**（2026-09-16，用户口径：「为什么明显里面还会有这段内容
这段无意义的内容为什么要展示在最显眼的地方，分清主次」）：最显眼的第一张卡只放
① 这次分析是谁（ASIN · 站点 · 区间 · 判定徽章）② 服务端的一句话结论（`headline`）
③ 数据可靠性的关键限制（**一行**小字：数据时效 + 公开数据调用次数 + 未收录数量；取数失败单独一行红色）。
此前这里并列了**四段平级小字** —— "未指定记录"的长句、数据块的排列顺序与"不可相加"声明、数据时效、
额度消耗与维度列举 —— 把真正该看的结论与数据块挤到下面。现在：**排列顺序说明与维度列举已删除**
（每块自带来源标注，"自家与公开数据不可相加"的口径写在每块的 `note` 里），
自动回落的提示压成标题旁的一个 Badge「自动打开最近一次 #N」。

**「ASIN 横向对比」表转置展示**（2026-09-16，用户口径：「数据明细内的本品竞品的数据对比…对比起来不方便，
我需要一一对应本品跟竞品」）：服务端给的表是**一行一个 ASIN、指标横铺**（`COMPARISON_COLUMNS` 10 列），
要比"本品与竞品的花费差多少"得在两行之间左右扫、中间还隔着 8 个单元格。现在明细页在渲染前把它
**转置成"一行一个指标、一列一个 ASIN"**（表头 `指标 | <ASIN>（本品） | <ASIN>（竞品）…`），
本品与竞品的值逐指标紧挨着。实现是纯函数 `comparison-table.ts`（`isComparisonTableBlock` /
`transposeComparisonTable`，有单测），**只重排、不做任何加减乘除** —— 因此对已落库的历史快照
立刻生效（若改服务端生成逻辑，只有新分析是新形态，用户当前看的那条仍是旧样子，两种形态并存更难理解）。
识别用"列键与 `COMPARISON_COLUMNS` 逐项一致"而不是标题文案；判据刻意从严，避免误伤 AI 助手回答里
同样 `dataset: amazon_ads_daily` 的表。

**「按日明细」升级为「按日对比（本品 vs 竞品）」**（2026-09-16，用户口径：「数据明细内的本品竞品的数据对比
…按日明细对比起来不方便，我需要一一对应本品跟竞品」，随后追加：「这样不够明显 应该这样：表头 本品 竞品，
然后再是本品字段和竞品字段」）：原来的「按日明细」是 AI 助手对**单个** ASIN 的载荷产物，**只有本品**；
想看"同一天竞品花了多少"只能回到「ASIN 横向对比」去对总量，逐日是断的。现在服务端 `buildDailyComparisonBlock`
产出一张**两行表头**的对比表：

```
                                    本品（B0SAMPLE01）                    竞品1（B0B3JGBH5）
日期         花费     销售额   ACoS(%)  订单  曝光    点击  销量 | 花费     销售额   ACoS(%)  订单  曝光    点击  销量
2026-08-02   128.61   383.75   33.51    9     17199   98    10     79.15    211.06   37.5     5     17199   98    4
```

- **两行表头靠表格块新增的 `groups` 能力**：`AnswerBlock.groups`（`[{ label, span }]`）→ `buildTableBlock({ groups })`
  → `answer-blocks.tsx` 渲染第一行分组行（首列自动 `rowSpan=2`）。**可选字段，不传时行为与改动前完全一致**
  （AI 助手的表格零影响，有一条端到端护栏断言"没有 `groups` 的表仍是单行表头"）。
- **为什么不把归属写进列标签**：上一版是单行表头 + `花费 本品` / `花费 竞品1` 这类后缀，同一组字段的归属被重复 7 遍，
  扫一眼看不出"哪几列属于谁"（用户原话"这样不够明显"）。分组表头把归属提到一整行，一组只写一次。
- **列按 ASIN 成组**（本品 7 列 → 竞品 7 列），与第一行的分组一一对应；角色序号按用户输入顺序
  （中间某个竞品没有数据也不会错位）。
- **整组列铺一层淡色底**（2026-09-16 追加，用户口径：「再为对应列填充对应颜色 颜色不要太鲜艳能看出来就行
  颜色淡一点」）：颜色取主题的**分类色** `--chart-1..5`（深浅两套主题各自有值，不是硬编码色值），
  透明度压得很低 —— 数据行 **10%**、字段名表头 **20%**、分组表头 **25%**（形成一条色带）；
  首列（日期）保持中性。档位由服务端给（列上的 `tone` 与分组上的 `tone`），渲染层只映射类名：
  数据档位越界（0/负数/>5）一律**不加底色**，宁可无色也不要用错色。
  注意 Tailwind 不会为拼接出来的类名生成样式，所以三组类名是**写全的静态映射**。
- **零额外查询**：竞品的按日数据一直在内存里 —— `analyzeCompetitor` 本来就为每个 ASIN 各调了一次
  `amazonPerformancePayload`（之前只用了汇总，日粒度被丢掉）。
- **日期取并集**，某 ASIN 缺的那天显示「—」（不折算 0）；**全部 ASIN 都没有按日数据时不产出该块**。

## 本品 vs 竞品的对比配色口径（2026-09-17）

用户口径：「竞品和本品的对比都参考按日对比（本品 VS 竞品）排版方式」。
基准是「按日对比」—— 每个 ASIN 一组列、**一组一个主题分类色**（本品 `chart-1`、竞品依次 `chart-2…`），
分组表头 25%、字段名表头 20%、数据格 10% 底色。现在这张表之外的两张对比表照此办理：

| 表 | 形态 | 归属表达 |
| --- | --- | --- |
| 按日对比（本品 vs 竞品） | 行 = 日期，列 = 每个 ASIN 一组 7 列 | 服务端给 `groups` + 列 `tone`（**基准，未改动**） |
| ASIN 横向对比 | 行 = 指标，列 = 一个 ASIN | `transposeComparisonTable`（`comparison-table.ts`）给每列补 `tone`（本品 1、竞品 2…） |
| 商品公开数据对比（表格视图） | 行 = 属性，列 = 一个 ASIN | `transposeProductTable`（`product-view.ts`）转置后同样补 `tone` |
| TOP 流量词 / 差评高频词 | 行 = 一个词，归属写在**角色列**里 | `applyRowTones`（`role-rows.ts`）给每行补 **`__tone` 行元数据** |

**为什么后两张表要"行级归属色"**（用户口径追问：「TOP 流量词为什么没有同步调整」）：
它们的形状是"一行一个关键词（或一个差评高频词）"，本品与竞品的行**混在同一张表里**、
归属由 `role` 列给出 —— 列上没法着色（同一列里混着两家），只能**整行铺一档淡色底**。
渲染层在 `AnswerBlock.rows` 上认这个可选的 `__tone`（见 `types.ts` 的字段说明），
读的是 `row.original` 而不是行索引，因此**排序后颜色跟着行走**；
`applyRowTones` 保证"本品永远第一档"（即使行序被打乱，例如差评高频词按词频排序），
同一 ASIN 的行大小写不同也归到同色；认不出（缺 `asin` / `role`）就原样返回，宁可不上色。

两条纪律：

- **配色只由 `tone` 决定，渲染层不做判断**：`answer-blocks.tsx` 的 `toneClass()` 把 `tone` 映射成
  **写全的静态类名**（Tailwind 不会为拼接出来的类名生成样式），`tone` 越界（0 / 负数 / >5）一律不加底色。
  前端补的 `tone` / `__tone` 只是"取哪一档主题色"，**不涉及任何业务数字计算**。
- **转置与上色只动展示层**：转置只重排、缺失一律 `null`（渲染层显示「—」），行归属色只加渲染元数据 ——
  两者都对**已落库的历史快照立刻生效**（服务端生成逻辑未动，老记录与新记录形态一致）。
  识别仍按结构化判据（`dataset` 标记 + 列键逐项一致 + 行内字段），**不按标题文案**。

只读检查（`verify-artifacts/check-competitor-findings-layout.mjs`，可传记录 id：
`node verify-artifacts/check-competitor-findings-layout.mjs http://localhost:5173 79`）读计算样式断言：
"（本品）列与（竞品）列的表头底色**都铺了色且两色不同**，数值列同样带归属色"、
"角色列归属表里**同一角色的行同色且都铺了色、不同角色不同色**"；
没有这类表（例如没勾公开数据维度的记录）时跳过而不误红。
共享渲染层另有一份护栏单测 `src/features/ai-agent/components/answer-blocks.test.tsx`：
**没有 `__tone` 的表单元格不带任何底色**（AI 助手的表格零影响）、带 `__tone` 时只给该行上色。

## 结论的处置：处理什么 / 怎么处理 / 去哪里处理（2026-09-17）

用户口径：「竞品与分析的结论与建议里面的需立即处理没有任何交互 继续处理是处理什么，如何处理
去哪里处理都没有」。经选项确认两条：**可点入口 + 三段式处置说明**；系统外动作**标注「系统外」
并给出具体步骤**。

改前的问题：每条结论只有一个 `action` **纯文字建议**，而且三类内容混在一起 ——
系统内能做的（"到「数据源与导入」上传报表"）、只能在亚马逊后台做的（"排查 Listing 转化要素"）、
以及只是判断的（"价格优势可支撑更高定价"）。徽章「需立即处理」是静态标签，点不动。

**数据模型**（服务端 `finding-fixes.mjs`）：每条结论带一个**稳定的诊断码 `code`**，
收口处按码补结构化处置方案 `fix`：

```jsonc
{
  "code": "acos_up",
  "fix": {
    "what": "本品 B0SAMPLE01 的 ACoS 相比上一等长区间明显上涨",
    "links": [{ "label": "看本次横向对比", "to": "/competitor-analysis/results" }],
    "offSystem": ["广告后台 → 按「花费降序」找出增量花费集中在哪些活动/关键词", "..."]
  }
}
```

三条纪律（改这块前先读）：

1. **按诊断码映射，不按标题文案**：标题是动态拼接的（`ACoS 环比上涨 57.05%`），按文案匹配
   改一个字就静默失效。新增一类结论时要给它一个码，并在 `finding-fixes.mjs` 里补方案
   （`finding-fixes.node-test.mjs` 会断言"每个已定义的码都能出非空方案"）。
2. **不给假链接**：`to` 必须是站内真实路由；前端 `FIX_ROUTES` 白名单**查不到就不渲染按钮**
   （服务端写错路径，界面上不会出现点进去 404 的入口）。`adminOnly` 的入口（数据源与导入）
   对普通员工不渲染 —— 宁可不给，也不给一个点进去被拒的按钮。
3. **入口参数由页面补**：服务端生成结论时**分析还没落库**（拿不到 `analysisId`），也拿不到类目关键词；
   因此 `analysisId` / `keyword` / `marketplace` 由页面通过 `linkContext` 传进来
   （结果页传 `effectiveId` + `marketKeyword`，详情页与任务详情页传各自的记录 id）。
   补不上的入口不渲染（例如没有类目关键词就不给"看这个类目的市场结构"）。

**生成点与收口**：自家结论在 `finalizeFindings(findings, context)` 补 `fix`；
公开结论由 `sellersprite-blocks.mjs` 生成、不走那条路径，因此在 `mergeFindings(local, public, context)`
处统一补 —— 两处都走同一个 `buildFix`，处置文案只有一份。

**向后兼容**：老快照没有 `code` / `fix`，前端回退到原来的 `action` 文字建议（端到端脚本有断言）。
要看新形态必须跑一次新分析（本模块的只读检查脚本覆盖不了老记录）。

只读/端到端检查：`node verify-artifacts/check-finding-actions.mjs`（**9/9**）——
真实登录后提交一次**零额度**分析（脚本会取消勾选全部公开数据维度，并断言页面上不出现非零额度预估），
然后断言「处理什么：」「去哪里处理：」与真实 href 入口、「系统外」步骤逐条列出、
以及老快照仍回退到文字建议。**注意它每次会真实产生一条分析记录**（自家报表、不消耗额度）。

## 结论的处置闭环：销账 + 自动核验（2026-09-17）

用户口径：「**用户修改完成后回到系统调整为修改完成**」。上一节解决的是"**怎么处理**"，
这一节解决"**处理完之后系统怎么认**"—— 两者是不同的两件事，别再混为一谈。

### 为什么不能做成"点一下就完成"

结论**不是持久化的记录**：`competitor_analyses.result` 只是当时的快照，每次分析都用当期数据
重新算一遍。因此：

- 状态挂在"某一次分析"上没有意义 —— 下次分析的 finding 是全新对象，挂上去等于每次都要重标；
- "点一下就算完成"会骗人 —— 数据没变，这条结论下次分析照样出现，用户会认为系统在说谎。

### 两段式（唯一形态）

状态按 **(账号, 诊断码 `code`, 处置目标 `target`)** 沉淀在 `competitor_finding_dispositions`
（**迁移 202**）。`target` 派生于 `targetAsins[0]`、回落到本品 ASIN ——
**用 ASIN 不用 SKU**：ASIN 是分析输入的单位，也是"本次分析是否评估过该目标"的判据（`result.asins`）。

| 状态 | 谁置的 | 含义 | 首页报警 |
| --- | --- | --- | --- |
| （无行） | —— | 待处理 | 计入 |
| `claimed` | 用户点「标记已处理」 | 只是**销账**，不代表已解决 | **不计入** |
| `verified` | **系统**在下次分析时判定不再命中 | 确实解决了 | **不计入** |
| `open` | **系统**在下次分析时打回 | 标记过已处理却仍命中（含复发），带 `reopen_count` | 计入 |
| `ignored` | 用户点「不处理」并**必填原因** | 用户的长期决定，**终局** | **不计入** |

核验规则（`planDispositionUpdates`，纯函数，单测 16 项）：

1. `claimed` + 不再命中 → `verified`；`claimed` + 仍命中 → `open`（`reopen_count + 1`，记本次 `verify_detail`）；
2. `verified` + 再次命中 → `open`（**复发**，要报警）；
3. `ignored` **永不自动改动** —— 用户已说不处理，再打回就是打扰；
4. **只在"本次分析评估过该 target"时才判定**（`result.asins` 含该 ASIN）：
   用户跑一次别的 ASIN 的分析，**绝不能**把所有待核验项判成"已解决"。
   这是本机制最容易犯、后果最严重的错（**虚假销账**），单测第一条护栏就是它。

核验在**落库路径**上调用：`POST /api/competitor-analyses`。
（2026-09-20 任务中心整体下线前，`task-center-runner.mjs` 这条后台执行路径也必须调核验 ——
否则"从任务中心跑的分析不理解账"，同一个功能会出现两套结果。将来若再引入后台任务执行器，
新执行器同样要在这里调用核验。）

### 界面（`findings-panel.tsx`）

每条结论底部一块（`[data-finding-disposition]`）：状态徽章 + **三个真按钮**：

- 「标记已处理」`[data-finding-claim]` → `claimed`；
- 「不处理」`[data-finding-ignore]` → 内联展开原因输入（**必填**，服务端也强制 400）→ `ignored`；
- 「复制处理步骤」`[data-finding-copy]` → 把 `what` + 系统外步骤复制走（贴群 / 工单）。

`claimed` / `ignored` 时出现「撤销标记」`[data-finding-undo]`（服务端删行）。**每一项都是真动作**，
没有一个是"点了没反应"的假按钮 —— 与"不给假链接"是同一条纪律。
（原先还有第四个按钮「提交后台分析任务」`[data-finding-task]` → 去任务中心，**2026-09-20 随任务中心
整体下线一并移除**；竞品分析自己的同步提交不受影响。）

打回时界面**如实说明**：「你标记过已处理，但后续分析仍然命中」+ 本次仍命中的事实（`verify_detail`）
—— 用户必须知道系统凭什么打回。

### 两个口径的分工（2026-09-17 **第二次修正**，别再改回去）

| 口径 | 字段 | 谁在用 | 回答的问题 |
| --- | --- | --- | --- |
| **快照判定** | `level` / `findingCount` | 快照详情、结果页头卡、**AI 对话里的记录列表** | 那次分析算出了什么（历史事实） |
| **未销账** | `openLevel` / `openFindingCount` / `clearedFindingCount` | **竞品分析历史表、首页「需处理的分析」与「最近分析」、概览统计** | 现在还要不要我处理 |

**修正的原因（用户实测反馈）**：「在分析结果页标记为已处理后历史分析为什么还是展示需立即处理」。
上一版把**列表**也归给"历史事实"口径，理由是"不篡改历史" —— 这个理由只对了一半：
快照判定确实是事实，但**列表要回答的是"这条记录现在还要不要我处理"**。
用户销账后回到列表仍看到红字「需立即处理」，唯一合理的解读就是"标记没生效"。

**结论**：列表（含首页「最近分析」）**一律用未销账口径**，并且有销账时补一句
「已销账 N 条」（`clearedFindingCount`）。这条由共享组件
`src/features/competitor-analysis/components/history-level-badge.tsx` 统一渲染 ——
两处各写一套必然分叉。

**`clearedFindingCount` 必须由服务端算**：它是"actionable 总数 − 未销账数"，
**不要**在前端拿 `findingCount - openFindingCount` 自己减 —— `findingCount` 含 `info` 级，
一条都没销账也会减出正数（列表会显示"已销账 1 条"）。服务端有单测守这条。

**这不是篡改历史**：原始判定仍然可以在快照与详情页里查到，只是换了列表这一列要回答的问题。

**唯一的例外**：AI 对话里的分析列表仍用快照判定（它回答的是"那次分析算出了什么"），
见下方「已知边界」。

老记录（迁移 203 之前落库、没有 `finding_keys`）缺 `openLevel` 时前端回落到 `level`；
`finding_keys`（轻量清单 `[{ code, target, level }]`）与快照同时写入，
就是为了列表算这几个数时**不必把几百 KB 的 `result` 读出来**。

### 历史记录（老快照）为什么一开始不能标记（2026-09-17 修，用户实测报上来）

**现象**：用户点开首页「需处理的分析」里的记录，结论上**没有**「标记已处理」按钮
（原话：「需立即处理的结论为什么不能标记」）。实测：`analysisId=79` 的处置块与按钮数均为 **0**。

**根因**：台账的键是 `(code, target)`，而 `code`（诊断码）是 2026-09-17 才随
`finding-fixes.mjs` 加进快照的 —— 更早落库的记录里 `findings` **没有 `code`**，
而 `FindingDispositionBlock` 的渲染条件是 `analysisId && code && dispositionTarget`，
于是**整块处置区不渲染**。**更关键的是：首页报警指向的恰恰是这些历史 high 记录**
（新分析常常只是 medium），所以这不是边缘情况而是**主路径** —— 用户看到"需立即处理"、
点进去却什么也做不了。

**修法**（迁移 **203** 回填 + 运行时同一套派生）：

1. `legacyCodeFor(finding, index)` 给没有码的**非 `info`** 结论派生**记录内位置键**
   `legacy:<index>` —— 快照是冻结的 JSON 数组，同一条记录每次读出来的下标完全一致，键稳定；
2. **回填与读取共用 `collectFindingKeys`**（迁移 203 回填历史记录；`attachDispositions` 读取时
   补上 `code` / `dispositionTarget` / `legacy`）—— 两处各写一套算法必然漂移，
   表现是"界面上有按钮、一点却 400（不属于该次分析）"；
3. **`legacy:*` 永不参与自动核验**：新分析里不可能出现这个键，硬核验会被判成
   "不再命中 → 已核验解决"（**假销账**）。`planDispositionUpdates` 显式跳过，单测有护栏；
4. 界面在这类结论的按钮**上方**如实说明：「来自处置功能上线前的历史快照，没有诊断码：
   可以手动销账，但系统不会在下次分析时自动核验它（想要自动核验，请用同参数重新分析一次）」。

**结果**：老记录**能销账**、首页报警可被清掉（实测 `openCount 2 → 1`，撤销后回到 2，
台账 `legacy:0|B0CTJGJL2T` 写入后撤销即删行），同时**不会**被误标成"已核验解决"。

### 已知边界（别当成 bug）

- **AI 助手的历史列表仍是快照口径**（`ai-agent/competitor-history.mjs` 调 `toHistoryItem` 不传台账）：
  它回答的是"那次分析算出了什么"，不是"现在还要处理什么"。对话里的列表与首页口径有意不同。
- **「提交后台分析任务」按钮已随任务中心下线移除（2026-09-20）**：它原本的语义是"让服务端后台
  再跑一次同参数分析"，**不是**"把系统外的活派给同事"。若将来要做后者，需要新的任务类型
  （超出本模块范围）；要做前者，则需要先恢复一套后台执行器。
- **核验依据的是数据，而报表是 T+1 或手工导入的**：用户当天改完广告、当天重新分析，
  很可能仍然命中（数据还没更新）。界面因此必须显示本次仍命中的事实，让用户自己能判断
  是"没改好"还是"数据还没进来"。
- 撤销标记是**删行**（语义 = 我什么都没标记过），不保留"曾标记过"的历史；
  打回（`open`）则保留行与 `reopen_count`。

## 额度与缓存（改这块前必读）

- 卖家精灵**按 HTTP 请求次数计费**（月付档普遍 1000–4000 次/月）。一次全维度分析（5 个 ASIN）≈ **22 次调用**：
  `public` 2 次/ASIN + `traffic` 1 次/ASIN + `reviews` 1 次/ASIN + `market` 固定 2 次。
- 因此：① 维度默认只开 `public`；② 结果一律**落库缓存**（`competitor_public_cache`，按 `kind + ASIN/nodeIdPath + marketplace`，默认 24 小时）；
  ③ 并发限制 4（实测限流 40 次/分钟，对单密钥）；④ 界面显示预估次数与「实际调用 / 缓存命中」。
- 缓存存的是**原始返回**而不是解析结果：解析逻辑会随需求变化，重新解析不需要再花钱调一次外部接口。

## 注意事项

- **ASIN 输入区保持"单框多值"（2026-09-16 试过结构化、当日按要求撤回，别再做回去）**：
  输入区是**一个多行 Textarea**，第 1 个 ASIN 视为本品、其余为竞品，分隔符（换行 / 逗号 / 顿号 / 分号）
  全部交给服务端 `parseAsinList`；前端只做**额度预估用的粗计数**（`countAsins`）与提交前的"是否为空"判断。
  曾按用户选择做成"本品一行 + 竞品可增删行"的角色化输入（含多值自动分流），用户随后要求改回单框
  （「输入框调整回之前那样 不使用逗号分割 使用换行分割即可」）—— 他要的是**把一列 ASIN 直接贴进来**，
  结构化输入把这一步变成了多步操作。**两个仍然成立的契约**：① 输入框 id 保持 `competitor-asin`
  （`?focus=asin` 深链与五个端到端脚本按它定位 / 填值；脚本里既有 `#competitor-asin` 也有
  `getByLabel(/ASIN/)` 两种定位，删了 id 或改了 Label 文案都会打断它们）；
  ② 提交只发一个 `inputValue`，**服务端按输入顺序分角色**，前端不得另立语义。
- **统计区间预设要与服务端同口径**：前端 `format.ts` 的 `WINDOW_OPTIONS` 与服务端
  `competitor-analysis.mjs` 的 `WINDOW_PRESETS` / `MAX_WINDOW_DAYS` 必须同时改 ——
  只改前端会出现"页面能选、提交被 400 拒绝"（2026-09-16 加「一年」时把上限从 180 放宽到 365 就是这个原因：
  预设天数不能超出服务端允许范围，365 也在自定义区间上限 366 之内）。
- **参数区（站点 / 对比基线 / 统计区间）以「同一行 + 宽度按内容给足即止」为准**（2026-09-16 用户口径）：
  三者都是"选一次"的参数，不该各自占 1/3 行宽，也不该让统计区间独占整行（上一版为塞下 6 个预设
  改的 `col-span-3` 就是这么留下的）。现为 `lg:grid-cols-[12rem_12rem_minmax(0,1fr)]`；改列宽时注意
  站点当前值「自动（按数据推导）」是这一行最长的文本（≈174px），列宽低于 12rem 会被 `line-clamp-1` 截断。
  公开数据三个维度同为一行（`sm:grid-cols-3`），卡片变窄靠 `min-w-0` 让 hint 换行而不是撑破卡片。
