# 责任田：认证模块

## 功能描述

负责内部登录、忘记密码、OTP 验证、认证布局和前端认证状态示例。

## 功能清单

- 登录页：提供公司内部账户登录入口，并提供自助注册入口。
- 自助注册：`/sign-up` 提交申请，账号以待审核状态落库，须管理员放行后才能登录。
- 忘记密码：保留密码找回表单，当前不从登录页暴露。
- OTP：保留一次性验证码输入和提交，当前不从登录页暴露。
- 认证状态：通过 Zustand 保存当前前端认证状态示例。
- 路由守卫：`_authenticated` 路由基于本地 mock 会话做前端访问拦截。

## 入口与出口

- 入口：`src/routes/(auth)/sign-in.tsx`、`sign-up.tsx`、`forgot-password.tsx`、`otp.tsx`。
- 出口：**认证成功后的落点（2026-09-18 实测确认，勿随意改）**：
  - **默认进首页 `/`**（仪表盘）——`user-auth-form.tsx` 的 `navigate({ to: redirectTo || '/', replace: true })`；
    OTP 验证成功后同样是 `/`（`otp-form.tsx`）。
  - **被守卫拦下时回原页**：`_authenticated/route.tsx` 在未登录时抛
    `redirect({ to: '/sign-in', search: { redirect: location.href } })`，登录表单把该参数交给
    `redirectTo`，因此"点开某个深层链接 → 被要求登录 → 登录后回到那个页面"。
    四种入口的实测落点：`/sign-in` → `/`、`/` → `/`、`/task-center` → `/task-center`、
    `/competitor-analysis` → `/competitor-analysis`。
  - **两条行为都有单测守住**（`user-auth-form.test.tsx`：默认跳 `/`、给了 `redirectTo` 就去那里），
    改动其一会让另一条一起红 —— 这是有意的：只允许"默认首页 + 回原页"这一种组合。
  - 用户口径（2026-09-18）确认**保留回原页**：直接登录进首页，会话失效被踢出后能接着做原来的事。

## API 明细

- `POST /api/auth/login`：`{ login, password }` → JWT（8 小时）+ 用户信息。**空密码与缺失密码一律 401，且不进入哈希比对**。
- `POST /api/auth/register`：**公开接口**（2026-10-14 新增）。`{ login, name, password }` → 201；账号以 `status='pending'` / `role='operator'` / `department=''` 落库，**不发 token**。密码强制 8–128 位，账号已存在 409，同 IP 每分钟 3 次（超限 429）。
- **登录提示按状态区分，但只在密码正确之后**：密码对 + 待审核 → 「账号正在等待管理员审核，通过后即可登录。」；密码对 + 已停用 → 「账号已被停用，请联系管理员。」；密码错误或账号不存在 → 仍是统一的「账号或密码错误。」。**这个顺序不能反**：注册接口本身会用 409 暴露「账号已存在」，所以对已输对密码的人说明状态不新增枚举面；而对密码错误者保持模糊，避免不用密码就白拿账号状态。
- `GET /api/auth/me`：当前用户信息（只读下发，写入由管理员在用户管理页完成）。
- `GET /api/users`、`POST /api/users`、`PATCH /api/users/:id`、`PATCH /api/users/:id/status`：用户管理（仅管理员）。
- **审核注册申请复用 `PATCH /api/users/:id/status`**：通过 = `enabled`，拒绝 = `disabled`（保留记录、日后可再启用），**不新增审核接口** —— 审核在数据上就是"把状态改掉"这一件事。
- `POST /api/users/:id/reset-password`：管理员重置密码；服务端校验长度 8–128，成功后写 `user_reset_password` 审计。
- 登录成功与失败**都**写审计（`action='login'`）：`detail.result` 为 success/failed，失败原因区分 `empty_credentials` / `unknown_account` / `bad_password` / `pending_account` / `disabled_account`。`detail` 只记账号，绝不记密码。注册动作另写 `action='user_register'`（`actor_id` 为空，detail 记 login / name / status）。

## 依赖关系

- 依赖：`src/features/auth/`、`src/stores/auth-store.ts`、`react-hook-form`、`zod`、`PasswordInput`、`InputOTP`。
- 被依赖：认证页路由、后续真实鉴权守卫、用户菜单退出逻辑。
- 共享字段：认证状态、用户会话信息、跳转目标。

## 影响范围

本次修复涉及登录错误提示，以及裸请求、SSE 的过期会话收口；登录接口契约、JWT 规则与角色权限未变。

修改认证模块可能影响登录入口、找回密码流程、OTP 验证、全局认证状态和 `_authenticated` 访问控制。真实鉴权接入还会影响 API 错误处理、401/403 跳转和会话刷新策略。

登录页使用 `AuthLayout` 的 `split` 变体；忘记密码和 OTP 页面继续使用默认 `centered` 变体。登录页视觉调整不改变 API、JWT、权限、路由守卫或数据库。

## 修改边界

- 可以改：认证页 UI、表单校验、认证状态封装、演示提交逻辑。
- 绝对不能动：未确认前不得切换第三方认证服务、不得新增真实权限规则。

## 注意事项

- **空密码必须拒绝（2026-09-14 修复，勿回退）**：历史实现把缺失的 `password` 当作空串去比对哈希（`bcrypt.compare('', hash)` 对空串哈希返回 `true`）。配合当时「重置密码允许置空」的行为，这构成一条**未认证者接管任意账号**的路径。现在登录接口在查库前就拒绝空/缺失密码，重置密码接口强制 8–128 位。改动登录逻辑时必须保留这条前置校验。
- **改密码即刻吊销旧 token（2026-09-14 已实现）**：`users.token_version`（迁移 3）在签发时写入 token 的 `ver`，`requireUser` 与 AI 模块的 `identityGuard` **都**回源比对，重置密码时 `+1`。两处必须同时改：AI 路由挂在独立 router 上、不共用 `requireUser`，漏一处旧 token 仍能访问 `/api/ai/*`。旧 token 没有 `ver` 声明时按 0 处理，与库内默认值一致，因此不会把所有在线用户踢下线。
- 当前认证守卫尚不完整，不要假设 `_authenticated` 已经具备真实权限保护。
- **`auth.loginAt` 的语义（2026-09-15 新增，勿误用）**：记录"本次页面会话内**成功登录**过"的时刻，只在 `setAccessToken` 时写入，且**只存内存**（进 cookie 的只有 token 与 user），登出与刷新页面都归零。公告弹窗（`features/announcements`）靠它区分"登录"与"刷新 / 站内跳转"，因此判断"要不要弹"时**不能**改用"token 是否存在"：cookie 里的 token 刷新后依然有效，分不出这两件事。将来新增登录入口（如 SSO 回调）必须走 `setAccessToken`，否则公告不会弹。
- 当前 `_authenticated` 守卫只检查本地 mock token 和本地过期时间，用于无后端接口阶段的前端收口。
- **自助注册（2026-10-14 起开放，取代此前「不保留注册入口」的约定）**：未登录访客可在 `/sign-up` 提交申请，落库 `status='pending'`；**待审核账号拿不到 token**，必须由管理员在「用户管理」页通过（置 `enabled`）后才能登录。前端守卫无需改动 —— pending 用户根本没有 token，`_authenticated` 天然进不去。
- **注册接口的三道防线（改这里之前先读）**：① `parseUserRegister` **丢弃**客户端传来的 `role` / `department`（注册者若能自选角色，就是一条自助提权路径）；② 密码强制 8–128 位（公开接口不能放过弱密码）；③ 同 IP 每分钟 3 次，**进程内存计数，只对单进程生效** —— 将来多实例部署必须换成共享存储（如 Redis），否则各实例各算各的窗口。
- **注册接口的密码口径与管理员开通接口不同**（注册 8–128、开通不校验）：这是**已知的口径差异**，本次刻意没顺手统一，避免改动影响既有调用方。要统一时两处一起改并补测试。
- 密码输入统一使用 `PasswordInput`。
- OTP 输入使用现有 OTP 组件，不重复造输入框。
- 接入真实 API 前，应先确认登录、刷新、退出、401 处理和持久化方案。
- 登录页品牌区装饰图分别提供浅色与暗色资产。
- 小于 `lg` 时隐藏桌面品牌区，只保留移动端品牌锁定和登录表单。
- 内部工作台开放**自助注册（提交后需管理员审核）**，仍不提供社交登录；忘记密码入口依旧不从登录页暴露。
- 品牌名统一使用「JHYP 智能工作台」，登录页主标题、品牌锁定、`AuthLayout` 居中变体标题必须一致。

## 约束

- 必须复用：`AuthLayout`、`PasswordInput`、shadcn/ui Form、Zod schema、`useAuthStore`。
- 验证要求：代码修改后运行 `pnpm run lint`、`pnpm run build`，表单行为修改需运行相关测试或手动验证。
