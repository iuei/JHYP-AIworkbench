# 责任田：用户管理

负责管理员查询、筛选、创建、编辑、停用、删除账号和重置密码的内部账号管理。姓名、部门、角色都由这里配置，用户侧只读。

## 边界与接口

- 页面路由：`/_authenticated/settings/users`
- 仅数据库中实时角色为 `admin` 且状态为 `enabled` 的用户可访问和操作。
- 查询与角色、状态筛选在前端基于当前用户列表组合执行。
- 接口：`GET/POST /api/users`、`PATCH /api/users/:id`、`PATCH /api/users/:id/status`、`POST /api/users/:id/reset-password`、`DELETE /api/users/:id`。
- **审核注册申请**：待审核（`status='pending'`）账号在列表页行内用「通过审核 / 拒绝」处理，**复用** `PATCH /api/users/:id/status`（通过 = `enabled`，拒绝 = `disabled`），不新增审核接口。
- 编辑接口仅允许修改姓名、部门和角色；管理员不能修改自己的角色或账号状态。
- 角色降级和账号停用都会保护最后一个已启用管理员。
- 角色中文文案由 `src/features/settings/user-labels.ts` 统一提供，与用户信息页共用。

## 自助注册与审核（2026-10-14）

- **来源**：用户可在登录页进入 `/sign-up` 自助提交申请（公开接口 `POST /api/auth/register`，见 `认证模块.md`），
  落库即 `status='pending'` / `role='operator'` / `department=''`。注册者**不能**自选角色或部门
  —— 服务端 `parseUserRegister` 直接丢弃这两个字段，防止变成一条自助提权路径。
- **待审核账号登不进去**：登录接口在**密码正确**的前提下会明确回「账号正在等待管理员审核，通过后即可登录。」，
  而不是含糊的「账号或密码错误。」。
- **审核就是改状态**：列表页对 `pending` 行显示「通过审核 / 拒绝」两个按钮，走的是同一个
  `PATCH /api/users/:id/status`，**没有新增审核接口**：
  - 通过 → `enabled`，对方立刻可以登录；
  - 拒绝 → `disabled`，**保留账号记录**（等于"不通过"而不是"删掉这个人"），日后仍可在列表里「启用」。
  拒绝走 `ConfirmDialog` 二次确认，文案写明"记录会保留"，避免管理员误以为拒绝会清空数据。
- **状态筛选新增「待审核」**且排在下拉首位；状态列用 `Badge` 强调「待审核」——
  它和「已停用」不是一回事：前者等着管理员动手，后者是已经出过结果的状态。
- **`pending` 不是管理员可设置的状态**：`parseUserStatusUpdate` 只接受 `enabled` / `disabled`
  （单测 `parseUserStatusUpdate accepts only supported statuses` 守着这条）。把已有账号改回"待审核"
  没有业务含义，只会让用户以为自己被退回了申请。
- **前端改动很小**：`ManagedUser.status` 类型扩为三态，`filterUsers` 无需修改（本就按 status 泛化）。

## 删除账号（2026-09-16）

- **语义是硬删除**：`DELETE /api/users/:id` 直接删 `users` 行，外键按建表时就定好的口径级联 ——
  业务数据（AI 会话与消息、经验沉淀、我的 ASIN、竞品分析、公告已读、快捷偏好、工作任务）是
  `ON DELETE CASCADE`，随账号一并消失；审计与「创建人 / 审核人」字段是 `ON DELETE SET NULL`，
  记录保留、操作人置空。**没有回收站，不可恢复**。
- **三道闸一个都不能少**：① 仅管理员（`requireAdmin` + 事务内 `hasCurrentAdminAccess`，
  挡住"刚被降级的人还在删"）；② 不能删自己；③ 必须至少保留一个已启用管理员。
  后两条是纯函数 `describeUserDeletionBlock()`（`server/user-management.mjs`，有单测），
  与改角色 / 停用共用同一套口径。
- **并发安全**：事务内先 `SELECT ... FOR UPDATE` 锁住「启用中的管理员」集合，再判闸门 ——
  否则两个管理员并发互删时，双方都会读到"还有一个管理员"而各删各的。
- **审计必须记身份**：`ai_audit_logs.actor_id` 对 `users` 是 `SET NULL`，被删者自己的历史记录
  会失去操作人；所以这次删除的 `detail` 里落 `login / role / status / department / lastLoginAt`，
  否则事后只留一个指向已不存在行的 `target_id`，回答不了"删的是谁"。
- **登录名随删除释放**：`users.login` 是唯一约束，删除后可以重新开通同名账号（这是硬删除的附带效果）。
- 前端入口：用户管理页行内「删除」（`destructive`）→ `ConfirmDialog` 二次确认（写明会连带清空哪些数据、
  不可恢复）；确认框只负责选中账号，**点行内按钮不发请求**；自己的那一行按钮直接禁用。
  错误原因（如"必须至少保留一个已启用管理员。"）原样来自服务端，前端不复述规则。
- 审计台可见性：`ACTION_LABELS`（`src/features/ai-agent/pages/audit-console.tsx`）补齐了账号类动作文案
  （开通 / 修改 / 启停 / 重置密码 / **删除账号**）—— 该表既是显示文案也是筛选下拉的数据源，
  此前这五个动作只能显示英文原文且无法按动作筛选。

## 批量启用 / 停用（2026-09-17）

- **入口**：列表页工具区第二排的「批量启用」「批量停用」（工具区走全站统一的 `ListPageShell`，见 `表格与列表规范.md`）。
  **未勾选任何行时两个按钮置灰**，禁用原因写在 `title`（与行内「停用 / 删除」对自己置灰的既有做法一致）。
- **走逐条调用既有接口**（`PATCH /api/users/:id/status`），**不新增批量接口**：服务端的
  "必须至少保留一个已启用管理员"是逐条判定的，批量接口要么重复这套规则、要么在部分失败时给出含糊结果。
  前端用 `Promise.allSettled` 收全部结果：成功的生效（toast 汇报条数），失败的把**服务端原话**
  （如"必须至少保留一个已启用管理员。"）透出来 —— 与删除、改角色同一条口径：规则由服务端说，前端不复述。
- **自己的账号那一行复选框禁用**：行内「停用 / 删除」本来就对自己置灰，若这里能勾上，
  批量操作会绕过那道闸门、拿到一个服务端拒绝的结果。
- **选择范围只在当前页**（`useRowSelection` 的既有口径）：翻页、改筛选、改每页条数都 `clear()` ——
  跨页累积会让"批量停用 12 个"变成一次看不全的批量操作。
- **停用要确认、启用不拦**：`ConfirmDialog` 只挂在批量停用上（停用会让对方立刻登不进去，属影响他人的动作；
  启用是恢复性操作，多一次点击只增加负担）。
- **验证**：`server/verify-page-shell.mjs` **38/38**（真实 Chrome，**只做禁用态断言、从不点击批量按钮**，
  勾选的行断言后立即取消）、`src/features/settings/users/index.test.tsx` **6/6**。

## 部门字段

- 落库在 `users.department VARCHAR(40) NOT NULL DEFAULT ''`，由迁移 `server/user-migrations.mjs` version 2 添加。
- 开通账号时可选填；编辑时可修改或清空（提交空串即清空）。
- `parseUserUpdate` 对未携带 `department` 的请求返回 `null`，SQL 用 `COALESCE($3, department)` 保留原值 —— 老调用方不会把已有部门静默清空。
- 用户信息页通过 `GET /api/auth/me` 只读展示该字段；新增或改名时必须同步该接口的 SELECT 与 `src/features/settings/profile/types.ts`。
